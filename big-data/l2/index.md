2. **Ієрархія виконання запитів:** Зв'язок Application $\to$ Jobs $\to$ Stages $\to$ Tasks та аналітичний розрахунок хвиль виконання (*waves of tasks*).

## 1. Архітектура Apache Spark та розподілене виконання

### 1.1. Фізична та інтуїтивна суть
> **💡 Інтуїція:** Якщо Hadoop MapReduce після кожної операції зберігав проміжні результати на повільний жорсткий диск (HDFS), то Apache Spark виконує всі проміжні перетворення безпосередньо в оперативній пам'яті (In-Memory). Це робить його в 10–100 разів швидшим.

```text
┌─────────────────────────────────────────────────────────────────┐
│                          DRIVER PROGRAM                         │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ SparkContext / SparkSession                               │  │
│  │  • Побудова плану запиту (DAG)                            │  │
│  │  • Розбиття на Stages та Tasks                            │  │
│  │  • Планування та моніторинг виконання (Task Scheduler)     │  │
│  └───────────────────────────────────────────────────────────┘  │
└────────────────────────────────┬────────────────────────────────┘
                                 │ Координація завдань
                                 ▼
                     ┌───────────────────────┐
                     │    CLUSTER MANAGER    │
                     │(YARN / K8s / Standal.)│
                     └───────────┬───────────┘
            ┌────────────────────┴────────────────────┐
            ▼                                         ▼
┌───────────────────────────────┐ ┌───────────────────────────────┐
│          WORKER NODE          │ │          WORKER NODE          │
│ ┌───────────────────────────┐ │ │ ┌───────────────────────────┐ │
│ │         EXECUTOR          │ │ │ │         EXECUTOR          │ │
│ │ (JVM-процес, кеш, пам'ять)│ │ │ │ (JVM-процес, кеш, пам'ять)│ │
│ │ ┌───────────┐┌───────────┐│ │ │ │ ┌───────────┐┌───────────┐│ │
│ │ │  Slot 1   ││  Slot 2   ││ │ │ │ │  Slot 1   ││  Slot 2   ││ │
│ │ │  (Task)   ││  (Task)   ││ │ │ │ │  (Task)   ││  (Task)   ││ │
│ │ └───────────┘└───────────┘│ │ │ │ └───────────┘└───────────┘│ │
│ └───────────────────────────┘ │ │ └───────────────────────────┘ │
└───────────────────────────────┘ └───────────────────────────────┘
```

### 1.2. Основні компоненти кластера

* **Cluster:** Група об'єднаних мережею машин (Node / Virtual Machines).
* **Driver Program:** Центральний координатор програми.
  - Запускає `main()` код і створює `SparkSession`.
  - Формує логічний та фізичний граф обчислень (DAG).
  - Розподіляє та призначає задачі (Tasks) виконавцям.
  - У разі збою Executor-а драйвер перепризначає його задачі іншим вузлам.
  - **Критичне правило:** Драйвер сам майже ніколи не обробляє сирі дані (якщо не викликати `collect()`).
* **Executor:** Окремий процес Java Virtual Machine (JVM), що працює на Worker Node.
  - Отримує код задачі від драйвера, завантажує дані своєї партиції та виконує обчислення.
  - Зберігає кешовані дані в оперативній пам'яті або локальному диску.
  - *На платформі Databricks завжди діє співвідношення 1 Executor на 1 Worker Node*.
* **Slot (Core / Thread):** Мінімальна неподільна одиниця паралелізму.
  - 1 слот = 1 доступне процесорне ядро/потік.
  - **1 слот виконує рівно 1 задачу (Task) одночасно.**
* **Partition (Партиція):** Неподільний фрагмент (chunk) загального датасету. Кожна задача опрацьовує рівно одну партицію.

---

### 1.3. Формула оцінки паралелізму та розрахунок хвиль задач (Task Waves)

Нехай у кластері є $W$ воркерів, кожен з яких має $C$ ядер процесора, а датасет розбитий на $P$ партицій.

1. **Загальна кількість доступних слотів ($S$):**
   $$S = W \cdot C$$
2. **Кількість одночасних задач:** не більше ніж $S$.
3. **Кількість послідовних хвиль задач ($N_{\text{waves}}$):**
   $$N_{\text{waves}} = \left\lceil \frac{P}{S} \right\rceil$$

> **📌 Приклад із тесту:**
> Кластер містить 2 воркери по 4 ядра CPU в кожному. DataFrame розбитий на 200 партицій.
> - Кількість паралельних слотів: $2 \times 4 = 8\text{ слотів}$.
> - Кількість хвиль задач: $200 / 8 = 25\text{ хвиль}$.
> *Висновок:* Кількість партицій визначає загальний обсяг роботи, а кількість слотів — скільки роботи виконується паралельно в одну мить.

## 2. Ієрархія виконання: Application $\to$ Job $\to$ Stage $\to$ Task

1. **Application:** Повна програма користувача (код у ноутбуці або jar/python скрипт).
2. **Job:** Набір обчислень, що запускається у відповідь на виклик **Action** (наприклад, `.count()` або `.save()`).
3. **Stage:** Логічний блок задач, які можуть виконуватися послідовно без пересилання даних через мережу (*Pipelining*).
   - **Межа між Stage завжди визначається операцією Shuffle (Wide Transformation)**.
   - Stage не може вважатися завершеним, доки не виконаються **всі** його задачі.
   - *Проблема Straggler (відстаючого):* якщо одна задача виконується довго через перекіс даних (Data Skew), вона затримує весь Stage.
4. **Task:** Елементарна одиниця роботи, яка надсилається драйвером в один Slot для обробки однієї партиції.

## 3. Базові абстракції даних: RDD проти DataFrame

| Властивість | RDD (Resilient Distributed Dataset) | DataFrame |
|---|---|---|
| **Рівень абстракції** | Низькорівневий API | Високорівневий структурований API |
| **Структура даних** | Колекція сирих Java/Python/Scala об'єктів | Таблиця з іменованими колонками та строгою типізацією |
| **Оптимізація запитів** | **Відсутня** (виконується точно те, що написав інженер) | **Повна оптимізація** через Catalyst Optimizer та Tungsten |
| **Швидкість у Python** | Повільна (вимагає серіалізації Py4J між Python та JVM) | **Максимальна** (код виконується в оптимізованому рушії Tungsten на рівні C++) |
| **Формат представлення** | `rdd.map(lambda x: (x, 1))` | `df.groupBy("country").count()` або Spark SQL |

## 4. Операції у Spark: Transformations та Actions

### 4.1. Трансформації (Transformations) — Ледачі обчислення (Lazy Evaluation)
Трансформації приймають один DataFrame і повертають новий DataFrame. Вони **не виконують реальних обчислень**, а лише записують крок у граф операцій (DAG).

#### А. Вузькі трансформації (Narrow Transformations):
- **Суть:** Кожна вхідна партиція впливає щонайбільше на одну вихідну партицію. Обмін даними між різними нодами через мережу **відсутній**.
- **Приклади:** `filter()`, `select()`, `map()`, `withColumn()`, `drop()`.
- **Швидкість:** Дуже висока, підтримують конвеєризацію (*pipelining*).

#### Б. Широкі трансформації (Wide Transformations):
- **Суть:** Дані з однієї вхідної партиції потрібні для побудови багатьох вихідних партицій. Вимагають перерозподілу даних між усіма нодами кластера через мережу — **Shuffle**.
- **Приклади:** `groupBy()`, `reduceByKey()`, `join()`, `distinct()`, `repartition()`, `orderBy()`.
- **Швидкість:** Повільні, створюють новий Stage та призводять до скиду даних на диск.

```text
  NARROW (Без перемішування)             WIDE (Shuffle / Перемішування)
  Partition 1 ──────► Partition 1       Partition 1 ──┬───► Partition 1
  Partition 2 ──────► Partition 2       Partition 2 ──┼───► Partition 2
  Partition 3 ──────► Partition 3       Partition 3 ──┴───► Partition 3
```

---

### 4.2. Дії (Actions)
Операції, які вимагають повернення конкретного значення користувачеві або збереження результату на диск. Саме виклик Action змушує Spark запустити DAG на виконання!
- **Приклади:** `collect()`, `count()`, `first()`, `take(n)`, `show()`, `saveAsTable()`, `write.parquet()`.

> **💡 Інженерна порада щодо порядку трансформацій:**
> Намагайтеся групувати операції за патерном:
> $$\text{Narrow} \to \text{Narrow} \to \text{Wide} \to \text{Wide} \to \text{Narrow}$$
> Уникайте постійного чергування $\text{Narrow} \leftrightarrow \text{Wide} \leftrightarrow \text{Narrow} \leftrightarrow \text{Wide}$, оскільки кожна зміна провокує новий цикл запису на диск.

## 5. Вузькі місця: Shuffle проти Spill

### 5.1. Shuffle (Перемішування)
- **Що це:** Запланований розподіл та передача партицій мережею між різними вузлами для виконання групування чи об'єднання.
- **Ціна:** Запис проміжних shuffle-файлів на диск воркера, передача гігабайтів мережею, десеріалізація в новому процесорі.

### 5.2. Spill to Disk (Аварійний скид на диск)
- **Що це:** **Незапланований аварійний процес**, який виникає, коли для виконання операції (сортування, хеш-таблиця `groupBy`) не вистачає виділеної оперативної пам'яті (Execution Memory).
- **Механізм:** Щоб не впасти з помилкою `OutOfMemoryError (OOM)`, Spark вимушено записує частину блоків з RAM на локальний диск воркера, а потім знову зчитує їх.
- **Наслідок:** Катастрофічне падіння швидкості роботи (у 5–20 разів) через дискове введення/виведення (I/O).
- **Як лікувати Spill:**
  1. Збільшити пам'ять на Executor (`spark.executor.memory`).
  2. Збільшити кількість партицій (`repartition` або зміна `spark.sql.shuffle.partitions`), щоб розмір кожної партиції був меншим.
  3. Усунути перекіс даних (Data Skew).

## 6. Керування пам'яттю (Memory Management)

Уніфікований пул пам'яті всередині кожного Executor JVM:

```text
┌─────────────────────────────────────────────────────────────┐
│                       EXECUTOR MEMORY                       │
├───────────────┬─────────────────────────────────────────────┤
│ Reserved (300MB)│ Внутрішнє ядро Spark                      │
├───────────────┼─────────────────────────────────────────────┤
│ User Memory   │ Користувацькі структури, UDF, змінні        │
├───────────────┼─────────────────────────────────────────────┤
│ Spark Memory  │ ┌─────────────────────┬───────────────────┐ │
│ (Shared Pool) │ │  Execution Memory   │  Storage Memory   │ │
│               │ │  (Joins, Shuffles,  │  (DataFrames      │ │
│               │ │   Sorts, Aggregates)│   .cache(), bc)   │ │
│               │ └─────────────────────┴───────────────────┘ │
│               │ * Взаємне запозичення пам'яті (Borrowing)    │ │
└───────────────┴─────────────────────────────────────────────┘
```

> **⚠️ Чому `.cache()` може спричинити OOM або Spill?**
> Execution та Storage ділять спільний пул пам'яті та можуть позичати її один в одного. Якщо ви закешували занадто великий датасет, Storage-пам'ять витіснить вільне місце, і наступний `JOIN` або `groupBy` не матиме достатньо Execution-пам'яті, що спровокує масивний **Spill на диск** або аварійний краш!

## 7. Вбудовані оптимізатори та практичні поради (Best Practices)

1. **Catalyst Optimizer:** Генерує оптимізований фізичний план виконання:
   - *Predicate Pushdown:* переміщує операцію `filter()` якомога ближче до джерела даних (наприклад, читає з Parquet лише потрібні рядки).
   - *Column Pruning:* читає з диска тільки ті стовпці, які згадані у запиті.
2. **Project Tungsten:**
   - Генерація машинного байт-коду на льоту (*Whole-Stage Code Generation*).
   - Ефективне управління двійковою пам'яттю поза купою JVM (*Off-Heap memory*), щоб уникнути пауз збирача сміття (Garbage Collector).
3. **Adaptive Query Execution (AQE):**
   - Динамічно оптимізує план виконання в процесі роботи (наприклад, автоматично перемикає SortMergeJoin на BroadcastJoin, якщо реальний розмір таблиці після фільтрації виявився малим; автоматично об'єднує дрібні партиції).
4. **Broadcast Hash Join:**
   - Якщо одна з таблиць при `JOIN` мала (типово $< 10\text{ МБ}$), вона транслюється (broadcast) на всі воркери. Це **повністю усуває Shuffle** великої таблиці!
   - Синтаксис: `big_df.join(broadcast(small_df), "id")`.
5. **Уникайте звичайних Python UDF:**
   - Стандартний Python UDF змушує Spark серіалізувати кожен рядок з Java JVM у процес Python, виконати функцію і передати результат назад. Завжди використовуйте вбудовані функції `pyspark.sql.functions` або векторизовані Pandas UDF (на базі Apache Arrow).

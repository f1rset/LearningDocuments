## 🔑 1. Ключові концепції та формули (TL;DR для тесту)

> **Головна ідея:** Spark виконує обчислення в оперативній пам'яті (In-Memory). Робота будується як граф залежностей (DAG) з лінивими трансформаціями, які запускаються діями (Actions). Головні вороги продуктивності — мережевий Shuffle та дисковий Spill.

* 📌 **Слоти та паралелізм:**
  - $1\text{ слот} = 1\text{ CPU ядро} = 1\text{ Task одночасно}$.
  - Загальна кількість слотів: $S = \text{Воркери} \times \text{Ядер на воркер}$.
  - Кількість хвиль задач для $P$ партицій: $N_{\text{waves}} = \lceil P / S \rceil$.
* 📌 **Ієрархія:** $\text{Application} \to \text{Job (виклик Action)} \to \text{Stage (розділені Shuffle)} \to \text{Task (1 слот, 1 партиція)}$.
* 📌 **RDD vs DataFrame:** RDD — низькорівневий, без оптимізацій, повільний у Python; DataFrame — структурований, оптимізований Catalyst & Tungsten.
* 📌 **Narrow vs Wide:**
  - **Narrow (Вузькі):** `filter`, `select`, `map`, `withColumn`. Без обміну мережею, швидкі.
  - **Wide (Широкі):** `groupBy`, `join`, `distinct`, `repartition`, `orderBy`. Створюють **Shuffle** та межу між **Stages**.
* 📌 **Shuffle vs Spill:**
  - **Shuffle:** Запланований перерозподіл даних через мережу між нодами (норма для групувань).
  - **Spill to Disk:** Аварійний скид блоків з RAM на диск через нестачу Execution Memory. Головний вбивця швидкості!

## 📊 2. Порівняння операцій та оптимізацій (Test Table)

| Операція / Компонент | Тип | Що робить | Вплив на мережу / диск | Коли застосовувати |
|---|---|---|---|---|
| `filter()`, `select()` | Narrow | Фільтрує / відбирає колонки | 0 мережевого трафіку | **Завжди якомога раніше (Predicate Pushdown)** |
| `groupBy()`, `distinct()` | Wide | Агрегує або шукає унікальні | Повний **Shuffle** через мережу | Після фільтрації сирих даних |
| `broadcast(df)` | Join opt | Розсилає малу таблицю на всі воркери | **0 Shuffle** великої таблиці | Коли одна таблиця $< 10\text{ МБ}$ (або до кількох сотень МБ) |
| `.repartition(n)` | Wide | Змінює к-сть партицій рівномірно | Повний **Shuffle** | Для усунення Data Skew або перед важким записом |
| `.coalesce(n)` | Narrow | Зменшує к-сть партицій без shuffle | Без Shuffle (локальне злиття) | При збереженні результату (тільки на зменшення!) |
| `.cache()` / `.persist()` | Storage | Зберігає DataFrame в RAM | Займає пам'ять Storage Pool | Коли один DataFrame читається багаторазово |

## 🛠️ 3. Патерни та правила тюнінгу (Rules of Thumb)

* 🔹 **Порядок трансформацій:** Прагніть послідовності `Narrow -> Narrow -> Wide -> Wide -> Narrow`. Уникайте чергування `Narrow <-> Wide <-> Narrow <-> Wide`.
* 🔹 **Розмір партиції:** Ідеальний розмір однієї партиції в пам'яті Spark — **від 100 МБ до 200 МБ**. Занадто дрібні партиції створюють оверхед на планування задач; занадто великі — призводять до Spill на диск та OOM.
* 🔹 **Кешування:** Кешуйте тільки якщо датасет використовується двічі чи більше в різних Actions. Ніколи не викликайте `.cache()` без подальшого `.unpersist()`.
* 🔹 **Заборона на Python UDF:** Звичайні Python UDF вбивають швидкість (десеріалізація Java $\to$ Python). Використовуйте стандартний `pyspark.sql.functions` або Pandas UDF (PyArrow).

## ⚠️ 4. Підводні камені та пастки на тестах

* 🚨 **Питання про `collect()`:** Виклик `df.collect()` стягує **весь розподілений датасет на драйвер**. Якщо датасет має розмір 50 ГБ, а в драйвера 4 ГБ пам'яті — драйвер моментально впаде з `OutOfMemoryError`. Для перегляду використовуйте `df.show(5)` або `df.take(5)`.
* 🚨 **Чому впало після `.cache()`:** Пам'ять Execution і Storage ділять спільний пул. Кеш може "відкусити" забагато пам'яті, спровокувавши Spill або OOM у наступному `groupBy`.
* 🚨 **Збіг кількості задач і слотів:** Кількість одночасних задач лімітована слотами, а не кількістю партицій. Якщо партицій 1000, а слотів 10 — вони виконуватимуться у 100 послідовних хвиль.

## 📌 1. Вступ та сховища даних (NoSQL, DWH, Data Lake, Lakehouse)

### Ключові концепції:
* **Модель 3V:** Volume (ТБ $\to$ ПБ), Velocity (швидкість генерації та обробки), Variety (структуровані, напівструктуровані JSON/XML, неструктуровані $\approx 90\%$).
* **Додаткові V:** Veracity (достовірність/шум), Value (бізнес-цінність), Variability (мінливість схем у часі).
* **Batch vs Stream:** Batch — накопичені великі порції за період (години, дні); Stream — безперервний потік подій з низькою затримкою (мілісекунди/секунди, наприклад fraud detection).
* **Schema-on-Write (DWH):** Схема перевіряється перед записом. Помилки відхиляються. Висока якість, висока ціна.
* **Schema-on-Read (Data Lake):** Дані записуються як є (без схеми). Схема накладається читачем. Ризик виникнення **Data Swamp**.
* **Lakehouse:** Відкрите дешеве об'єктне сховище (Data Lake) + транзакційний шар (Delta Lake), що додає **ACID, schema enforcement та time travel**.

### Порівняльна матриця сховищ:
| Критерій | NoSQL | Data Warehouse (DWH) | Data Lake | Lakehouse |
|---|---|---|---|---|
| **Транзакції** | Часто BASE (Eventual) | **Повний ACID** | Немає | **Повний ACID** |
| **Схема** | Гнучка / без схеми | **Schema-on-Write** | **Schema-on-Read** | **Schema Enforcement & Evolution** |
| **Формати** | JSON, Key-Value | Тільки структуровані | Усі формати (сирі, медіа) | **Parquet + транзакційний лог** |
| **Storage / Compute** | Зв'язані | Часто зв'язані | **100% розділені** | **100% розділені** |

## 📌 2. Apache Spark: Архітектура, Виконання та Оптимізація

### Формули та розрахунки паралелізму:
* **Загальна кількість слотів:**
  $$S = \text{Кількість воркерів} \times \text{Ядер на воркер}$$
* **Кількість хвиль задач для $P$ партицій:**
  $$N_{\text{waves}} = \left\lceil \frac{P}{S} \right\rceil$$
  *Приклад:* 2 воркери по 4 ядра ($S = 8$), 200 партицій $\implies 200 / 8 = 25$ хвиль задач.
* **Ідеальний розмір однієї партиції:** **100 МБ – 200 МБ**.

### Компоненти та ієрархія:
* **Driver:** Планує граф обчислень (DAG), призначає задачі слотам, координує збої. Не обробляє сирі дані.
* **Executor:** JVM-процес на Worker Node. Виконує задачі (Tasks) та зберігає дані в кеші.
* **Ієрархія:** $\text{Application} \to \text{Job (виклик Action)} \to \text{Stage (межа — Shuffle)} \to \text{Task (1 слот, 1 партиція)}$.

### Narrow vs Wide трансформації:
* **Narrow:** `filter`, `select`, `map`, `withColumn`. Без обміну мережею, швидкі, працюють у конвеєрі (pipelining).
* **Wide:** `groupBy`, `distinct`, `join`, `repartition`, `orderBy`. Вимагають **Shuffle** (пересилання даних через мережу), створюють новий Stage.
* **Actions:** `collect()`, `count()`, `show()`, `take()`, `saveAsTable()`. Запускають обчислення.

### Shuffle vs Spill to Disk:
* **Shuffle:** Плановий розподіл партицій через мережу для групування. Вимагає запису на диск проміжних файлів.
* **Spill to Disk:** **Аварійний скид блоків з RAM на диск** через нестачу Execution Memory. Найбільший вбивця швидкості!
  - *Лікування:* збільшити пам'ять екзекутора, збільшити кількість партицій (`repartition`), усунути Data Skew.

### Пам'ять та пастки кешування:
* **Execution та Storage** ділять спільний пул пам'яті та позичають її один в одного.
* **Пастка:** Виклик `.cache()` може забрати надто багато пам'яті у Storage, через що наступний `JOIN` не матиме місця в Execution і піде у важкий **Spill на диск** або викличе `OutOfMemoryError`.

## 📌 3. Формати файлів: Рядкові, Колоночні та Delta Lake

### Row-oriented vs Columnar:
* **Рядкові (Avro, CSV, JSON):** Оптимальні для запису (OLTP) та вибірки цілих рядків (`SELECT * WHERE id = 1`). Стандарт для Kafka — **Apache Avro**.
* **Колоночні (Parquet, ORC):** Оптимальні для аналітики (OLAP, агрегації).
  - **Projection Pushdown:** читання тільки потрібних колонок з диска.
  - **Predicate Pushdown (Data Skipping):** пропуск цілих Row Groups завдяки $\min / \max$ статистикам.
  - **Колоночне стиснення:** один тип даних стискається алгоритмами RLE, Dictionary, Bit-Packing у рази щільніше.

### Delta Lake:
* **Архітектура:** `Parquet Data Files + _delta_log/ (JSON commit logs)`.
* **ACID:** Читачі читають тільки файли з успішних комітів, ніколи не бачать битих файлів.
* **Time Travel:** `SELECT * FROM tbl VERSION AS OF 3` або `TIMESTAMP AS OF '2026-01-01'`.
* **Compaction:** `OPTIMIZE my_table` (злиття дрібних файлів у великі $\approx 1\text{ ГБ}$) + `Z-ORDER BY (col)` (багатовимірне сортування для Data Skipping).
* **Трійка конкурентів:** Delta Lake (Databricks), Apache Iceberg (Netflix), Apache Hudi (Uber).

## 📌 4. Моделювання даних, Medallion Architecture та Data Quality

### Школи моделювання:
* **Bill Inmon (Top-down):** Корпоративне DWH у 3NF (єдине джерело правди) $\to$ вітрини даних.
* **Ralph Kimball (Bottom-up):** Розмірне моделювання (Dimensional Modeling), схеми «Зірка» за бізнес-процесами.
* **Крок назад Кімболла (3NF $\to$ 2NF):** Навмисна денормалізація вимірів у схемі «Зірка». Безпечна, бо в аналітиці немає частих оновлень рядків (немає update anomalies), зате усуваються коштовні `JOIN` на кожному звіті!

### Таблиці фактів та вимірів:
* **Зернистість (Grain):** Що саме описує один рядок факту (наприклад, одна позиція в чеку).
* **Факти:**
  - *Additive:* можна сумувати скрізь (`revenue`).
  - *Semi-additive:* можна сумувати скрізь, крім часу (`bank_balance`).
  - *Non-additive:* не можна сумувати взагалі (`unit_price`, margin %).
* **Виміри:**
  - *Conformed:* спільний стандартизований вимір для різних фактів (`dim_date`).
  - *Role-Playing:* один вимір відіграє кілька ролей у факті (`order_date`, `ship_date`).
  - *Junk:* збірний вимір для різнорідних низькокардинальних прапорців (`is_gift`, `pay_type`).

### Slowly Changing Dimensions (SCD Type 2):
* Створення нового рядка для фіксації зміни з полями: `sk` (Surrogate Key), `business_key`, `is_current`, `effective_date`, `expiry_date`.
* **Правило напіввідкритого інтервалу:**
  $$\mathbf{[\text{effective\_date},\, \text{expiry\_date})}$$
  *Початкова дата — включно, кінцева — виключно!* Писати `>= expiry_date` заборонено (вертає два записи).
* **Чому замало одного MERGE:** `MERGE` вміє або оновити, або вставити за збігом ключа. Він не вміє закрити старий рядок І вставити новий для того самого ключа одночасно. Потрібно два проходи: (1) `MERGE` на закриття, (2) `INSERT` на відкриття.

### Medallion Architecture (Databricks):
* **Bronze:** Сирий інжест, Append-only, точна копія джерела.
* **Silver:** Очищені, дедупліковані, узгоджені таблиці (часто 3NF), карантин помилок.
* **Gold:** Готові вітрини за схемою «Зірка», бізнес-агрегації для BI та аналітики.

### Data Quality та патерн Quarantine:
* **Закон концентрації дефекту:** Похибка в $0.07\%$ рядків (155 з 228 000) може спотворити підсумковий `SUM(revenue)` на десятки відсотків! Агрегація концентрує аномалії.
* **Чому Drop гірший за Quarantine:**
  - `Drop` (видалення через `WHERE`) знищує докази та реальні гроші без аудиторського сліду.
  - `Quarantine` розділяє потік: валідні рядки пишуться в `silver`, биті — в `quarantine` з колонкою `_failed_rules`.
* **Рівняння закриття балансу даних (The Closing Equation):**
  $$\text{Отримано} = \text{Доставлено (Silver)} + \text{Відхилено (Quarantine)} + \text{Видалено дублікатів}$$
  Дозволяє закрити баланс перед аудитом і виправити биті замовлення через процедуру **Re-drive**.

### Питання 1: Які базові 3V визначають феномен Big Data і які додаткові характеристики виділяють?
**Відповідь:**
- **Базові 3V:**
  1. **Volume (Обсяг):** Величезні масиви інформації (терабайти, петабайти), які не вміщуються в пам'ять або диски однієї машини.
  2. **Velocity (Швидкість):** Високий темп генерації та необхідність обробки в реальному часі (стрими, сенсори, фінансові біржі).
  3. **Variety (Різноманітність):** Співіснування структурованих, напівструктурованих (JSON) та неструктурованих (відео, аудіо, тексти) форматів.
- **Додаткові характеристики:**
  - **Veracity:** Достовірність даних та відсутність шуму.
  - **Value:** Практична цінність інсайтів, отриманих із даних.
  - **Variability:** Мінливість швидкості надходження та зміна структури в часі.
  - **Complexity:** Складність зіставлення десятків різних джерел.

### Питання 2: У чому принципова різниця між концепціями Schema-on-Write та Schema-on-Read?
**Відповідь:**
- **Schema-on-Write (характерна для RDBMS та Data Warehouse):** Схема таблиці суворо задається заздалегідь. Під час запису дані валідуються на відповідність типам і обмеженням; якщо рядок не відповідає схемі, запис відхиляється. Це гарантує ідеальну якість, але сповільнює первинне завантаження.
- **Schema-on-Read (характерна для Data Lake):** Дані зберігаються в «сирому» форматі без будь-якої попередньої валідації схеми під час завантаження. Схема накладається лише тоді, коли аналітичний рушій (наприклад, Spark або Presto) зчитує ці дані для виконання запиту. Це дозволяє зберігати будь-які дані дешево і швидко, але переносить ризик помилок на етап аналітики.

### Питання 3: Чому з'явилася концепція Lakehouse і яку проблему Data Lake та Data Warehouse вона вирішує?
**Відповідь:**
- **Data Warehouse** чудово забезпечує транзакції ACID, швидкий SQL та BI-звітність, але погано працює з неструктурованими даними і коштує занадто дорого при петабайтних обсягах.
- **Data Lake** дозволяє дешево зберігати будь-які обсяги неструктурованих та сирих даних на об'єктному сховищі (S3/ADLS) з розділенням вартості Compute/Storage, але страждає від відсутності транзакцій (ACID), через що перетворюється на «болото даних» (Data Swamp).
- **Lakehouse** реалізує транзакційний шар метаданих (наприклад, Delta Lake або Apache Iceberg) безпосередньо поверх дешевих файлів Parquet у Data Lake. Це дає:
  1. Повні гарантії ACID (надійні `UPDATE`, `DELETE`, `MERGE`).
  2. Можливість версійності та Time Travel.
  3. Контроль якості (Schema Enforcement).
  4. Єдину платформу одночасно для SQL/BI та Data Science/ML без необхідності підтримувати два окремих ізольованих сховища.

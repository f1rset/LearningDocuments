## 🔑 1. Ключові концепції та терміни (TL;DR для тесту)

> **Головна ідея:** Big Data виникає тоді, коли обсяг, швидкість або різноманітність інформації перевищують ліміти одного сервера, змушуючи переходити від традиційних реляційних баз даних до розподілених сховищ та обчислювальних кластерів.

* 📌 **Модель 3V:**
  - **Volume (Обсяг):** ТБ $\to$ ПБ $\to$ ЕБ даних.
  - **Velocity (Швидкість):** Швидкість надходження (Batch vs Real-time streams).
  - **Variety (Різноманітність):** Structured (таблиці), Semi-structured (JSON, XML), Unstructured ($\approx 90\%$ — медіа, логи, текст).
* 📌 **Розширені V:** **Veracity** (достовірність/шумність), **Value** (практична бізнес-корисність), **Variability** (сезонність/зміна схем), **Complexity** (складність інтеграції), **Visualization** (інтерпретованість).
* 📌 **Batch vs Stream:**
  - *Batch:* великі порції за інтервал (нічні звіти, низька терміновість, висока затримка).
  - *Stream:* подія за подією / мікропакети (мілісекунди, fraud detection, IoT моніторинг).
* 📌 **Schema-on-Write vs Schema-on-Read:**
  - *Schema-on-Write (DWH):* схема перевіряється під час запису (ETL). Помилки блокують завантаження.
  - *Schema-on-Read (Data Lake):* дані пишуться як є (ELT), схема накладається читачем.
* 📌 **Data Swamp (Болото даних):** Data Lake без структури, версійності та перевірки якості даних, у якому неможливо знайти достовірну інформацію.
* 📌 **Lakehouse:** Парадигма, що додає **ACID, schema enforcement та time travel** поверх дешевого об'єктного сховища Data Lake (на базі форматів на зразок Delta Lake).

## 🛠️ 3. Інженерні правила та евристики (Rules of Thumb)

* 🔹 **Правило 90%:** Близько 90% усіх новостворених даних у світі є неструктурованими. Якщо інфраструктура розрахована лише на структуровані таблиці — вона втрачає більшу частину контексту.
* 🔹 **Compute / Storage Decoupling:** Головна фінансова перевага сучасних хмарних сховищ — платити за зберігання окремо (дешеві копійки за гігабайт на S3), а обчислювальні вузли (Spark clusters) підіймати лише на час виконання розрахунків.
* 🔹 **Коли обирати Lakehouse:** Якщо в компанії є потреба і в класичних BI-звітах (потрібен SQL та ACID), і в машинному навчанні / роботі з сирими даними (потрібен Data Lake).

## ⚠️ 4. Підводні камені та типові пастки на тестах

* 🚨 **Пастка з транзакціями в NoSQL:** NoSQL-бази забезпечують горизонтальне масштабування саме завдяки послабленню вимог ACID (часто жертвуючи узгодженістю Consistency заради Availability та Partition Tolerance — теорема CAP).
* 🚨 **Пастка з Data Lake:** Без транзакційного шару (Delta Lake / Iceberg) звичайний Data Lake не дозволяє робити надійні `UPDATE` та `DELETE` (потрібно повністю переписувати файли-партиції вручну).
* 🚨 **Пакетний чи потоковий:** Якщо завдання формулюється як «виявлення шахрайських транзакцій банку під час проведення платежу» — це виключно **Stream Processing** (затримка має бути < 100 мс). Якщо «нарахування кешбеку в кінці місяця» — це **Batch Processing**.

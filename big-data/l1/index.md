## 🎯 Мета та ключові питання лекції

1. **Визначення Big Data та фундаментальні властивості:** Базові характеристики $3\text{V}$ (Volume, Velocity, Variety) та розширені метрики (Veracity, Value, Variability, Complexity, Visualization).
2. **Класифікація даних та обробки:** Структуровані, напівструктуровані та неструктуровані дані. Пакетна (Batch) проти потокової (Stream / Real-time) обробки.
3. **Еволюція систем зберігання даних:** 
   - Реляційні СКБД та NoSQL (переваги горизонтального масштабування проти втрати ACID).
   - Data Warehouse (DWH) — аналітичні сховища, Schema-on-Write, транзакційність.
   - Data Lake — дешеве об'єктне сховище, Schema-on-Read, загроза "Data Swamp".
   - Lakehouse — сучасна парадигма об'єднання найкращого з DWH та Data Lake.
4. **Екосистема Databricks:** Єдина хмарна платформа аналітики та машинного навчання на базі Apache Spark та Delta Lake.

## 1. Що таке Big Data: Джерела та класифікація $V$-властивостей

### 1.1. Фізична та інтуїтивна суть
> **💡 Інтуїція:** Big Data — це не просто «багато терабайтів». Це стан, коли обсяг, швидкість надходження або різноманітність даних перевищують можливості традиційних реляційних баз даних на одному сервері, вимагаючи розподілених систем збереження та паралельних обчислень.

#### Джерела генерації даних:
1. **Люди (Human-generated):**
   - $\approx 5$ нових профілів у Facebook створюється щосекунди.
   - $\approx 41.6\text{ млн}$ повідомлень надсилається у WhatsApp щохвилини.
   - 1 година перегляду відео на Netflix генерує $\approx 644\text{ МБ}$ трафіку.
2. **Машини та сенсори (Machine-generated):** IoT-пристрої, телеметрія, фітнес-трекери, камери відеоспостереження, серверні логи.
3. **Організації (Organization-generated):** Фінансові транзакції, ERP/CRM системи, платіжні операції, медичні картки.

---

### 1.2. Класичні характеристики: Модель $3\text{V}$

```text
                  ┌──────────────────────┐
                  │       BIG DATA       │
                  └──────────┬───────────┘
         ┌───────────────────┼───────────────────┐
         ▼                   ▼                   ▼
    ┌──────────┐       ┌───────────┐       ┌───────────┐
    │  VOLUME  │       │ VELOCITY  │       │  VARIETY  │
    │  (Обсяг) │       │(Швидкість)│       │(Різноманіт│
    │ ТБ / ПБ  │       │ Стримінг  │       │  ність)   │
    └──────────┘       └───────────┘       └───────────┘
```

1. **Volume (Обсяг):** Кількість накопичених даних. Вимірюється терабайтами ($10^{12}\text{ байт}$), петабайтами ($10^{15}\text{ байт}$) та ексабайтами. Дані більше не вміщуються на один жорсткий диск чи сервер.
2. **Velocity (Швидкість):** Темп генерації, надходження та необхідної обробки. Дані генеруються безперервно (IoT, транзакції на біржах, кліки на веб-сайтах) і часто вимагають реакції у субсекундному масштабі (Real-time).
3. **Variety (Різноманітність):** Спектр форматів та типів даних:
   - **Структуровані (Structured):** Сувора реляційна схема (таблиці SQL, CSV, реляційні БД).
   - **Напівструктуровані (Semi-structured):** Мають внутрішні маркери або структуру, але без фіксованої реляційної схеми (JSON, XML, HTML, логи).
   - **Неструктуровані (Unstructured):** Не мають формалізованої моделі даних (текст листів, аудіо, відео, зображення, знімки з камер). **Становлять $\approx 90\%$ усіх світових даних!**

---

### 1.3. Розширені властивості Big Data (Beyond 3Vs)

* **Veracity (Достовірність / Якість):** Рівень довіри, шумності та правдивості даних. Дані з різнорідних джерел часто містять дублікати, пропуски або помилки сенсорів.
* **Value (Цінність):** Здатність витягувати практичні бізнес-інсайти (ROI, прогнозування поведінки користувачів, оптимізація витрат). «Дані — це нова нафта, але вона корисна лише після переробки».
* **Variability (Мінливість):** Непостійність потоку даних, сезонні піки (наприклад, Black Friday), зміна схем із часом (Schema Drift).
* **Complexity (Складність):** Необхідність зіставлення, очищення та зв'язування даних із десятків різних джерел.
* **Visualization (Візуалізація):** Зрозуміле представлення результатів складного аналізу для бізнес-користувачів через дашборди.

## 2. Парадигми обробки: Batch vs Streaming

| Критерій | Пакетна обробка (Batch Processing) | Потокова обробка (Stream Processing) |
|---|---|---|
| **Суть** | Обробка заздалегідь накопиченого блоку даних за період | Безперервна обробка кожної події або мікропакетів на льоту |
| **Затримка (Latency)** | Години, хвилини (High latency) | Мілісекунди, секунди (Low / Real-time latency) |
| **Обсяг порції** | Великі статичні масиви (Historical data) | Поодинокі записи або невеликі вікна (Sliding / Tumbling windows) |
| **Типові задачі** | Нічні звіти, розрахунок місячних премій, навчання моделей ML | Виявлення шахрайства (Fraud detection), моніторинг серверів, IoT-алерти |
| **Інструменти** | Hadoop MapReduce, Apache Spark (Batch) | Apache Flink, Apache Spark Streaming, Kafka Streams |

## 3. Еволюція сховищ даних: NoSQL, DWH, Data Lake та Lakehouse

### 3.1. NoSQL бази даних (Not Only SQL)
Створені для подолання обмежень горизонтального масштабування реляційних СКБД.
- **Типи:** Ключ-значення (Redis), Документні (MongoDB), Колоночні сімейства (Cassandra), Графові (Neo4j).
- **Переваги:**
  - Горизонтальне масштабування (*Scale-out*) додаванням звичайних вузлів.
  - Гнучка схема (*Schema-agnostic / Flexible schema*).
  - Дуже низька затримка запису/читання (Low Latency).
  - Вбудована реплікація та висока доступність (*Fault tolerance*).
- **Виклики та обмеження:**
  - Обмежена підтримка транзакцій: більшість систем орієнтовані на **BASE** (Basically Available, Soft state, Eventual consistency) замість суворого **ACID**.
  - Складність аналітичних аналізів: відсутність складних `JOIN`, необхідність проектування структури строго під конкретні запити.
  - Власний синтаксис запитів (Vendor-specific query languages).

---

### 3.2. Data Warehouse (DWH, Сховище Даних)
Аналітична база даних, оптимізована для читання та побудови звітів (OLAP).
- **Приклади:** Snowflake, Amazon Redshift, Google BigQuery, Teradata.
- **Принцип:** **Schema-on-Write** (схема визначається перед завантаженням, дані проходять суворий ETL).
- **Переваги:**
  - 100% відповідність вимогам **ACID**.
  - Висока продуктивність складних аналітичних SQL-запитів (`JOIN`, агрегації).
  - Зрілість технологій та готовність для BI (PowerBI, Tableau).
- **Недоліки:**
  - Не вміє ефективно працювати з неструктурованими даними (відео, зображення, сирі логи).
  - Дуже висока вартість зберігання при петабайтних масштабах (compute та storage часто тісно пов'язані).
  - Складність інтеграції з потоковими даними в режимі реального часу.

---

### 3.3. Data Lake (Озеро Даних)
Централізований репозиторій для зберігання будь-яких даних у їхньому первинному, сирому вигляді.
- **Технології:** Amazon S3, Azure Data Lake Storage (ADLS), Google Cloud Storage (GCS), HDFS.
- **Принцип:** **Schema-on-Read** (схема накладається лише в момент зчитування даних аналітичним рушієм).
- **Переваги:**
  - Зберігання будь-яких форматів (CSV, Parquet, JSON, PNG, MP4).
  - Дуже низька вартість хмарного сховища.
  - Повне розділення вартості зберігання (*Storage*) та обчислень (*Compute*).
- **Недоліки (Проблема Data Swamp):**
  - **Відсутність транзакцій ACID:** якщо запис перервався, у сховищі залишаються пошкоджені файли.
  - **Брак контролю якості:** відсутність валідації схеми призводить до того, що озеро перетворюється на «болото даних» (Data Swamp).
  - Повільні аналітичні запити через відсутність індексів та статистики.

---

### 3.4. Парадигма Lakehouse: Поєднання найкращих світів

> **Концепція Lakehouse:** Архітектура, яка реалізує транзакційні гарантії, структуру та керування даними з Data Warehouse безпосередньо поверх дешевого та масштабованого об'єктного сховища Data Lake.

```text
┌─────────────────────────────────────────────────────────────┐
│                 BI, SQL Analytics, AI & ML                  │
├─────────────────────────────────────────────────────────────┤
│   LAKEHOUSE LAYER (Delta Lake, Apache Iceberg, Apache Hudi)  │
│    • ACID Transactions  • Schema Enforcement & Evolution    │
│    • Time Travel / Versioning  • Unified Batch & Streaming  │
├─────────────────────────────────────────────────────────────┤
│          CHEAP OBJECT STORAGE (Data Lake: S3 / ADLS)         │
│          Відкриті формати файлів (Apache Parquet)           │
└─────────────────────────────────────────────────────────────┘
```

## 4. Платформа Databricks

* **Що це таке:** Хмарна уніфікована аналітична платформа, створена засновниками Apache Spark.
* **Призначення:** Поєднує Data Engineering, Data Warehousing, Data Science та машинне навчання (ML/AI) в одному просторі.
* **Фундамент:** Побудована навколо **Apache Spark** (обчислювальний розподілений рушій) та **Delta Lake** (транзакційний шар Lakehouse).
* **Позиція на ринку:** Багаторічний лідер у звітах Gartner Magic Quadrant для платформ Data Science та Machine Learning.

## 📊 Зведена порівняльна таблиця сховищ даних

| Характеристика | NoSQL | Data Warehouse (DWH) | Data Lake | Lakehouse |
|---|---|---|---|---|
| **Основне призначення** | Високонавантажений OLTP, швидкий key-value доступ | Аналітичні BI-звіти, OLAP на структурованих даних | Зберігання сирих та неструктурованих даних | Універсальне: BI, SQL, Streaming, ML |
| **Типи даних** | Структуровані, Semi-structured (JSON) | Строго структуровані | Будь-які (структуровані, сирі, фото, відео) | Будь-які (Parquet + метадані) |
| **Схема** | Schema-flexible / Schema-less | **Schema-on-Write** (сувора валідація) | **Schema-on-Read** (без валідації при записі) | **Schema Enforcement & Evolution** |
| **Підтримка ACID** | Обмежена (зазвичай BASE) | **Повна (ACID)** | **Відсутня** | **Повна (ACID)** |
| **Вартість зберігання** | Середня | Дуже висока | Дуже низька | Дуже низька (хмарне сховище) |
| **Compute & Storage** | Часто зв'язані | Традиційно зв'язані (у хмарах частково розділені) | **Повністю розділені** | **Повністю розділені** |

## ⚠️ Підводні камені та типові помилки на тестах

1. **Плутанина між Schema-on-Read та Schema-on-Write:**
   - DWH використовує *Schema-on-Write* — дані не потраплять у таблицю, якщо вони не відповідають типам і колонкам схеми.
   - Data Lake використовує *Schema-on-Read* — ви можете завантажити будь-який битий JSON, і помилка виникне лише тоді, коли аналітик спробує його прочитати.
2. **Міф: «Data Lake замінює Data Warehouse»:**
   - Data Lake не може повноцінно замінити DWH без транзакційного шару (Delta Lake / Iceberg), оскільки він не гарантує узгодженості даних для звітності.
3. **90% неструктурованих даних:**
   - На тестах часто запитують співвідношення structured/unstructured: левова частка сучасних даних ($\approx 90\%$) є **неструктурованою** (відео, зображення, логи, аудіо).

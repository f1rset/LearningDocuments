### Питання 1: Чому запит `SELECT AVG(Age) FROM users WHERE ID > 100` виконується набагато швидше на Parquet, ніж на CSV чи Avro?
**Відповідь:**
- **Рядковий формат (CSV / Avro)** зберігає всі колонки рядка разом. Щоб порахувати середній вік, рушій змушений прочитати з диска кожен байт усіх інших колонок (`name`, `address`, `bio` тощо).
- **Колоночний формат (Parquet)** зберігає значення кожної колонки окремо. Спрацьовує:
  1. **Projection Pushdown:** З диска зчитуються лише колонки `Age` та `ID`. Усі інші 50 колонок взагалі не підіймаються у пам'ять, що зменшує навантаження на диск на 90%+.
  2. **Predicate Pushdown / Data Skipping:** Кожен блок Parquet (Row Group) містить метадані з мінімальним та максимальним значенням `ID`. Якщо для блоку $\max(ID) \le 100$, весь блок з мільйона рядків пропускається без зчитування.
  3. **Стиснення:** Колонка `Age` містить тільки схожі цілі числа, тому стискається алгоритмами Bit-packing/RLE у рази щільніше.

### Питання 2: Як влаштований Delta Lake всередині і чому він забезпечує транзакційність ACID поверх безтранзакційного сховища Amazon S3?
**Відповідь:**
- Сховище Amazon S3 саме по собі не підтримує транзакції ACID: якщо процес запису файлів перервався посередині, у бакеті залишаються пошкоджені файли.
- **Delta Lake вирішує це через транзакційний журнал `_delta_log/`**:
  - Реальні дані зберігаються у незмінних (*immutable*) файлах **Apache Parquet**.
  - На кожну операцію запису, оновлення чи видалення в папку `_delta_log/` записується новий нумерований JSON-файл фіксації (наприклад, `00000000000000000001.json`).
  - У цьому файлі вказано список операцій: які файли Parquet було додано (`add`), а які вважаються видаленими (`remove`).
  - Будь-який читач спочатку читає `_delta_log/` і формує актуальний знімок (*snapshot*) дійсних файлів. Недописані або пошкоджені файли невдалої транзакції ніколи не потрапляють у `_delta_log/`, тому читачі їх ніколи не побачать.

### Питання 3: Які переваги та головні сценарії використання формату Apache Avro порівняно з Apache Parquet?
**Відповідь:**
- **Формат Avro** є рядковим двійковим форматом, у заголовок якого вшивається схема даних у форматі JSON.
- **Переваги:**
  1. Швидкий запис поодиноких подій без необхідності буферизувати та перепаковувати масивні колоночні блоки.
  2. Першокласна підтримка еволюції схеми (Schema Evolution) зі зворотною сумісністю.
  3. Компактне бінарне представлення.
- **Головний сценарій:** Шини передачі повідомлень у реальному часі (наприклад, **Apache Kafka**) та потоковий інжест сирих подій. Для важкої аналітики потім використовують конвертацію з Avro в Parquet / Delta Lake.

## 🎯 Мета та ключові питання лекції

1. **Механізми організації даних на диску:** Порівняння рядкового (Row-oriented) та колоночного (Columnar) форматів збереження.
2. **Особливості аналітичних колоночних сховищ:** Механізми проекції (*Projection Pushdown*), фільтрації (*Predicate Pushdown / Data Skipping*) та алгоритми стиснення.
3. **Огляд ключових форматів Big Data:** CSV, JSON, Apache Avro, Apache ORC та Apache Parquet.
4. **Обмеження та виклики класичного Parquet:** Проблема оновлень (Updates/Deletes), відсутність транзакцій ACID, версійності та проблема дрібних файлів (*small files problem*).
5. **Delta Lake:** Архітектура поверх Parquet, транзакційний журнал `_delta_log/`, ACID-гарантії, Time Travel, операції MERGE/Upsert та альтернативи (Iceberg, Hudi).

## 1. Рядкове проти Колоночного збереження (Row vs Columnar Storage)

### 1.1. Фізична та інтуїтивна суть
> **💡 Інтуїція:** Уявіть таблицю співробітників з 50 колонками. Якщо вам потрібно порахувати лише середній вік (`AVG(Age)`), рядковий формат змушений прочитати з диска всі 50 колонок для кожного рядка, витрачаючи 98% ресурсів даремно. Колоночний формат зберігає значення однієї колонки поруч на диску, тому він читає **лише одну колонку Age**!

```text
ТАБЛИЦЯ:
ID | Name | Age | Department
1  | John | 35  | IT
2  | Jane | 28  | HR
3  | Bob  | 42  | Finance

РЯДКОВИЙ ФОРМАТ (Row-oriented: CSV, JSON, Avro):
[1, John, 35, IT] [2, Jane, 28, HR] [3, Bob, 42, Finance]
-> Усі поля одного запису лежать поруч на диску.

КОЛОНОЧНИЙ ФОРМАТ (Columnar: Parquet, ORC):
[1, 2, 3] [John, Jane, Bob] [35, 28, 42] [IT, HR, Finance]
-> Усі значення одного стовпця лежать неперервним блоком на диску.
```

---

### 1.2. Порівняння сценаріїв запитів

#### Запит 1 (Аналітичний / Агрегаційний):
```sql
SELECT AVG(Age) FROM employee WHERE ID > 2;
```
* **Переможець:** **Колоночний формат (Parquet)**.
* **Чому:** Прочитано лише колонки `Age` та `ID`. Колонки `Name` та `Department` взагалі не зчитуються з диска (*Projection Pushdown*).

#### Запит 2 (Точковий транзакційний / OLTP):
```sql
SELECT ID, Name, Age, Department FROM employee WHERE ID = 1;
```
* **Переможець:** **Рядковий формат (Avro, RDBMS)**.
* **Чому:** Усі атрибути конкретного співробітника лежать в одному блоці байтів на диску; колоночний формат змушений стрибати по 4 різних місцях файлу.

---

### 1.3. Чому колоночні формати настільки ефективні для аналітики?

1. **Projection Pushdown (Вибірка тільки потрібних стовпців):** З диска в RAM зчитуються виключно ті поля, які є у `SELECT` або `WHERE`.
2. **Predicate Pushdown & Data Skipping (Пропуск блоків без читання):**
   - У заголовках блоків (Row Groups) зберігаються метадані: $\min$ та $\max$ значення кожної колонки.
   - Якщо виконується `WHERE age > 50`, а для блоку зазначено `[min=20, max=45]`, Spark **пропускає весь блок без читання**!
3. **Колоночне стиснення (High Compression Ratio):**
   - Оскільки значення в колонці належать до одного типу даних (наприклад, тільки цілі числа або тільки назви міст), алгоритми стиснення працюють набагато краще (RLE — Run Length Encoding, Dictionary Encoding, Bit Packing, ZSTD, Snappy).
   - Розмір на диску зменшується у 4–10 разів порівняно з CSV.

## 2. Огляд ключових форматів Big Data

```text
┌──────────────────────┬──────────────────────┬──────────────────────┐
│     Apache Avro      │    Apache Parquet    │      Apache ORC      │
├──────────────────────┼──────────────────────┼──────────────────────┤
│  • Рядковий (Row)    │  • Колоночний (Col)  │  • Колоночний (Col)  │
│  • Бінарний + JSON   │  • Де-факто стандарт │  • Оптимізований     │
│    схема в хедері    │    Spark екосистеми  │    для Apache Hive   │
│  • Ідеальний для     │  • Складне вкладення │  • Стріпи (Stripes)  │
│    стримінгу/Kafka   │  • OLAP аналітика    │  • Легкі індекси     │
└──────────────────────┴──────────────────────┴──────────────────────┘
```

### 2.1. Apache Avro
- **Тип:** Рядковий бінарний формат.
- **Особливість:** Схема описується у форматі JSON і записується в заголовок кожного Avro-файлу.
- **Schema Evolution:** Повна підтримка зворотної та прямої сумісності схем (можна додавати нові поля з дефолтними значеннями).
- **Головна ніша:** Запис у реальному часі, шини повідомлень (Apache Kafka), подійні брокери.

### 2.2. Apache Parquet
- **Тип:** Колоночний двійковий формат.
- **Історія:** Створений спільно Twitter та Cloudera у 2013 році; став стандартом індустрії.
- **Внутрішня структура:**
  - **File:** містить один або кілька Row Groups.
  - **Row Group:** логічний зріз даних на фіксовану кількість рядків (типово 128 МБ – 512 МБ).
  - **Column Chunk:** дані конкретної колонки всередині даного Row Group.
  - **Page:** мінімальна одиниця читання/декомпресії.
- **Головна ніша:** Сховища Data Lake, аналітика в Spark, Trino, Snowflake, AWS Athena.

## 3. Обмеження звичайного Parquet на об'єктному сховищі (S3/ADLS)

Незважаючи на швидкість, «чистий» Parquet у Data Lake має фундаментальні недоліки:
1. **Відсутність оновлень (No in-place updates/deletes):** Хмарні сховища (S3) імутабельні. Щоб оновити один рядок у файлі розміром 500 МБ, потрібно прочитати весь файл, змінити рядок і записати **новий** файл.
2. **Відсутність ACID транзакцій:** Якщо джоба Spark впала на 90% запису, частина партицій уже лежить у сховищі. Інші читачі побачать пошкоджений, неповний датасет (*Dirty Reads*).
3. **Відсутність Time Travel / Data Versioning:** Неможливо відкотити помилковий запис чи подивитися стан таблиці станом на минулий вівторок.
4. **Проблема дрібних файлів (Small Files Problem):** Потокові запити щосекунди скидають файли по 10 КБ. Мільйони таких файлів перевантажують метастор і сповільнюють запити в тисячі разів.

## 4. Delta Lake: Транзакційний шар Lakehouse

> **Delta Lake** — це відкритий формат зберігання даних, який додає повноцінні транзакції **ACID, версійність, валідацію схеми та операції MERGE** поверх стандартних файлів Parquet.

```text
┌─────────────────────────────────────────────────────────────┐
│                       DELTA LAKE TABLE                      │
├─────────────────────────────────────────────────────────────┤
│   _delta_log/ (Транзакційний журнал: JSON commit logs)      │
│     ├── 00000000000000000000.json (Commit 0: Create table)  │
│     ├── 00000000000000000001.json (Commit 1: Append files)  │
│     └── 00000000000000000010.checkpoint.parquet             │
├─────────────────────────────────────────────────────────────┤
│   Parquet Data Files (Незмінні файли з реальними даними)    │
│     ├── part-0000-xxxx.parquet                              │
│     ├── part-0001-yyyy.parquet                              │
│     └── part-0002-zzzz.parquet                              │
└─────────────────────────────────────────────────────────────┘
```

### 4.1. Як працює Delta Lake всередині?
- Усі дані таблиці продовжують зберігатися у **стандартних Parquet-файлах**.
- Поруч з'являється системна папка `_delta_log/`, куди на кожен запис атомарно записується JSON-файл фіксації (*Commit Log*).
- У транзакційному лозі чітко зафіксовано: які саме Parquet-файли є актуальними (`add`), а які видалено або перезаписано (`remove`).
- Читач опитує `_delta_log/` і читає **тільки ті Parquet-файли, що входять в останній комміт**.

---

### 4.2. Ключові можливості Delta Lake

1. **ACID транзакції:**
   - Повна ізоляція запитів (Serializable / Write-Serializable).
   - Якщо операція впала — комміт не записується в `_delta_log/`, і читачі ніколи не побачать недописані файли.
2. **Time Travel (Подорож у часі / Аудит):**
   - Можливість виконати запит до будь-якої минулої версії таблиці за номером версії або міткою часу:
   ```sql
   SELECT * FROM silver_orders VERSION AS OF 5;
   SELECT * FROM silver_orders TIMESTAMP AS OF '2026-03-01 10:00:00';
   ```
3. **Уніфікація Batch та Streaming:**
   - Delta-таблиця може одночасно слугувати джерелом потоку (*Streaming Source*), приймачем потоку (*Streaming Sink*) та об'єктом пакетних запитів.
4. **Upserts / MERGE (Підтримка CDC та SCD):**
   - Нативна підтримка конструкції `MERGE INTO`, що дозволяє оновлювати існуючі рядки та додавати нові в одній атомарній транзакції:
   ```sql
   MERGE INTO target_table t
   USING source_updates s
   ON t.id = s.id
   WHEN MATCHED THEN UPDATE SET t.name = s.name
   WHEN NOT MATCHED THEN INSERT *;
   ```
5. **Оптимізація та боротьба з дрібними файлами:**
   - `OPTIMIZE my_table`: автоматично зливає тисячі дрібних файлів у великі блоки розміром $\approx 1\text{ ГБ}$.
   - `Z-ORDER BY (col1, col2)`: багатовимірне кластеризування даних для максимальної ефективності Data Skipping.

---

### 4.3. Альтернативні формати Lakehouse
Чи є Delta Lake єдиним варіантом? **Ні.** На ринку конкурують 3 відкритих формати:
1. **Delta Lake:** Створений Databricks, найглибша інтеграція зі Spark.
2. **Apache Iceberg:** Створений Netflix/Apple, популярний у хмарах AWS та екосистемі Snowflake/Trino.
3. **Apache Hudi:** Створений Uber, історично сфокусований на потоковому CDC-оновленні з мінімальною затримкою.

## 📊 Порівняльна матриця форматів файлів

| Параметр | CSV | Apache Avro | Apache Parquet | Delta Lake |
|---|---|---|---|---|
| **Тип зберігання** | Рядковий (Текст) | Рядковий (Бінарний) | Колоночний (Бінарний) | **Колоночний (Parquet + Log)** |
| **Стиснення** | Дуже слабке (gzip) | Середнє | **Дуже сильне (Snappy/ZSTD)**| **Дуже сильне** |
| **Швидкість аналітики**| Повільна | Середня | **Дуже висока** | **Максимальна (Data Skipping)**|
| **Schema Evolution**| Відсутня | **Повна (JSON)** | Підтримується | **Повна (Enforce & Evolve)** |
| **ACID / Транзакції**| Немає | Немає | Немає | **Так (Повний ACID)** |
| **Time Travel** | Немає | Немає | Немає | **Так (Версійність)** |
| **Оптимальна роль** | Обмін даними між людьми | Потоковий інжест (Kafka) | Data Lake зберігання | **Стандарт для Lakehouse / DWH**|

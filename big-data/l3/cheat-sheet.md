## 🔑 1. Ключові концепції (TL;DR для тесту)

> **Головна ідея:** Рядкові формати (Avro, CSV) створені для запису та точкового читання цілих рядків (OLTP, Kafka). Колоночні формати (Parquet, ORC) створені для аналітики (OLAP), де за рахунок читання лише потрібних колонок і пропуску блоків за статистикою досягається прискорення у сотні разів. Delta Lake надбудовує над Parquet журнал `_delta_log/`, перетворюючи файли на транзакційну ACID-таблицю.

* 📌 **Row vs Columnar:**
  - *Row-oriented (Avro, CSV):* дані зберігаються запис за записом. Швидкий запис, повільна агрегація.
  - *Columnar (Parquet, ORC):* дані зберігаються стовпець за стовпцем. Високе стиснення, швидка аналітика.
* 📌 **Projection Pushdown:** Читання з диска **тільки тих колонок**, які зазначені в `SELECT` або умовах.
* 📌 **Predicate Pushdown (Data Skipping):** Пропуск цілих Row Groups без читання даних завдяки збереженим $\min / \max$ значенням у метаданих файлу.
* 📌 **Avro:** Рядковий двійковий формат, схема вбудована у заголовок у JSON. Найкращий вибір для **Apache Kafka**.
* 📌 **Parquet:** Колоночний двійковий формат. Де-факто стандарт аналітики у Spark.
* 📌 **Delta Lake:** `Parquet Data Files + _delta_log/ (JSON commits)`.
  - Забезпечує **ACID, Time Travel, Schema Enforcement/Evolution, MERGE**.
* 📌 **Трійка альтернатив Lakehouse:** **Delta Lake** (Databricks), **Apache Iceberg** (Netflix), **Apache Hudi** (Uber).

## 📊 2. Порівняння запитів (Тестовий приклад)

| Запит | Який формат виграє | Чому |
|---|---|---|
| `SELECT AVG(price) FROM orders WHERE status = 'delivered'` | **Parquet (Columnar)** | Читаються лише 2 колонки (`price`, `status`). Решта 30 колонок взагалі не підіймаються з диска. |
| `SELECT * FROM users WHERE user_id = 'U12345'` | **Avro / RDBMS (Row)** | Потрібно витягнути всі атрибути одного користувача. Вони лежать у єдиному неперервному шматку байтів. |
| `INSERT INTO stream_events ...` (висока частота) | **Avro (Row)** | Легко дописувати окремі події без необхідності перепаковувати масивні колоночні блоки. |

## 🛠️ 3. Інженерні правила вибору формату (Rules of Thumb)

* 🔹 **Стримінг та інжест подій:** Використовуйте **Apache Avro**. Схема в заголовку захищає від битих повідомлень, а серіалізація працює швидко.
* 🔹 **Аналітичне сховище / Data Lake:** Використовуйте **Delta Lake** (або Parquet).
* 🔹 **Боротьба з дрібними файлами:** Періодично запускайте команду `OPTIMIZE table_name` у Delta Lake для злиття дрібних файлів у блоки по $\approx 1\text{ ГБ}$.
* 🔹 **Прискорення фільтрів:** Застосовуйте `Z-ORDER BY (col1, col2)` для колонок, за якими найчастіше виконується фільтрація у `WHERE`.

## ⚠️ 4. Підводні камені та пастки на тестах

* 🚨 **Міф: «Delta Lake змінює внутрішній формат Parquet»:**
  - **Ні!** Дані в Delta Lake зберігаються у звичайнісіньких валідних файлах Apache Parquet. Вся магія транзакцій криється у метаданих папки `_delta_log/`.
* 🚨 **Чому чистий Parquet не має ACID:**
  - На об'єктному сховищі (S3) немає операції блокування файлів чи транзакційного комміту на рівні директорії. Якщо процес запису впав, «хвіст» з недописаних файлів залишається і читачі бачать пошкоджені дані. Delta Lake вирішує це тим, що читач дивиться тільки на зафіксовані в `_delta_log/` файли.
* 🚨 **Time Travel не зберігає копії файлів безкінечно:**
  - Старі версії даних доступні доти, доки не буде виконано команду `VACUUM`, яка фізично видаляє з S3 файли, помічені як `remove` раніше встановленого періоду (за замовчуванням 7 днів).

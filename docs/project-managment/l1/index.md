## 🎯 Мета та ключові питання лекції
1. **Фундаментальні визначення:** Що таке Проект (*Project*), Програма (*Program*), Портфоліо (*Portfolio*). Критерії та елементи проекту за стандартами **ISO 21500, DIN 69901, PMBOK 7th ed., IPMA ICB 4.0**.
2. **Золотий трикутник проектного менеджменту (Project Management Triangle):** Баланс обмежень — Обсяг (*Scope*), Час (*Time/Schedule*), Бюджет/Вартість (*Cost/Budget*), Якість (*Quality*).
3. **Роль, функції та ділянки відповідальності Проектного Менеджера (Project Manager, PM):** Що повинен створювати, координувати та контролювати PM.
4. **Організаційний контекст та PMO:** Взаємодія Проекту з Організацією, організаційна культура, процеси, Project Management Office (PMO) та корпоративні цінності.
5. **Класифікація проектів та Життєвий цикл (Project Lifecycle):** Моделі життєвого циклу — Послідовна (*Waterfall*), V-модель (*V-Model*), Гнучка (*Agile: Scrum, Kanban, SAFe*), критерії вибору моделі.
6. **Майлстоуни (Milestones):** Точки контролю, аудити прогресу, рішення керівництва (*Pass, Conditional Pass, Fail*).

## 1. Вступ та контекст курсу

### 1.1. Мотивація та мета проектного менеджменту
* **Мотивація:** У сучасному технологічному світі успіх компаній залежить від здатності своєчасно та ефективно реалізовувати інноваційні задуми в умовах обмежених ресурсів і невизначеності.
* **Мета дисципліни:** Ознайомлення з базовими принципами, методами, інструментами та стандартами організації, планування та управління IT-проектами на всіх етапах їхнього життєвого циклу.

### 1.2. Базова термінологія та стандарти
Курс базується на загальноприйнятих світових стандартах та методологіях:
* **PMI PMBOK Guide** (*Project Management Body of Knowledge, 6th & 7th editions*)
* **ISO 21500 / ISO 21502** (*Guidance on project management*)
* **IPMA ICB 4.0** (*Individual Competence Baseline*)
* **DIN 69901** (*Project management systems*)
* **Automotive SPICE (ASPICE)** (*Process assessment model*)

## 2. Основні визначення проектного менеджменту

### 2.1. Що таке Проект (Project)?

Порівняння визначень за провідними світовими стандартами:

| Стандарт | Визначення Проекту (Project Definition) |
| :--- | :--- |
| **ISO 21500:2012** | Унікальний набір процесів, що складається з узгоджених і контрольованих робіт з датами початку та завершення, які виконуються для досягнення цілі. (*A unique set of processes consisting of coordinated and controlled activities with start and end dates, performed to achieve an objective.*) |
| **PMI PMBOK 7th ed. (2020)** | Тимчасове підприємство, спрямоване на створення унікального продукту, послуги або результату. (*A temporary endeavor undertaken to create a unique product, service, or result.*) |
| **IPMA ICB 4.0 (2015)** | Унікальне, тимчасове, міждисциплінарне починання, спрямоване на досягнення узгоджених цілей у межах визначених обмежень і вимог. (*A unique, temporary, multi-disciplinary and organized endeavor to realize agreed deliverables within predefined constraints and requirements.*) |
| **DIN 69901:2012** | Починання, яке суттєво характеризується унікальністю умов у своїй сукупності (ціль, обмеження в часі, фінансах, персоналі, специфічна організаційна структура). |

#### Ключові атрибути будь-якого Проекту:
1. **Унікальність (Uniqueness):** Результат проекту завжди відрізняється від попередніх (навіть якщо технології типові).
2. **Тимчасовість (Temporary Nature):** Чітко визначені дата початку (*Start Date*) та дата завершення (*End Date*). Проект не є безкінечним процесом.
3. **Цільова спрямованість (Goal-driven):** Існує заради досягнення конкретної бізнес-цілі або створення унікального Продукту / Послуги.
4. **Обмеженість ресурсів (Resource Constraints):** Фіксований або лімітований бюджет, обладнання, команда.
5. **Специфічна організаційна структура:** Тимчасова команда під керівництвом призначеного менеджера.

```text
Операційна діяльність (Operations)           Проектна діяльність (Projects)
┌─────────────────────────────────┐           ┌─────────────────────────────────┐
│ • Повторювана, рутинна робота   │           │ • Унікальна діяльність          │
│ • Підтримка поточного бізнесу   │    VS     │ • Створення нового результату   │
│ • Неперервна в часі             │           │ • Обмежена в часі (Start / End) │
│ • Мета: стабільність та якість  │           │ • Мета: впровадження змін       │
└─────────────────────────────────┘           └─────────────────────────────────┘
```

### 2.2. Проект, Програма та Портфоліо

```text
                   ┌───────────────────────────────────────────┐
                   │           ПОРТФОЛІО (Portfolio)           │
                   │ Стратегічні цілі всієї організації        │
                   └─────────────────────┬─────────────────────┘
                                         │
                 ┌───────────────────────┴───────────────────────┐
                 ▼                                               ▼
   ┌───────────────────────────┐                   ┌───────────────────────────┐
   │    ПРОГРАМА 1 (Program)   │                   │    ПРОГРАМА 2 (Program)   │
   │ Група пов'язаних проектів │                   │ Спільна бізнес-мета       │
   └─────────────┬─────────────┘                   └─────────────┬─────────────┘
                 │                                               │
        ┌────────┴────────┐                             ┌────────┴────────┐
        ▼                 ▼                             ▼                 ▼
 ┌─────────────┐   ┌─────────────┐               ┌─────────────┐   ┌─────────────┐
 │  Проект A   │   │  Проект B   │               │  Проект C   │   │  Проект D   │
 └─────────────┘   └─────────────┘               └─────────────┘   └─────────────┘
```

* **Проект (Project):** Одиничне починання для досягнення конкретного продуктового результату.
* **Програма (Program):** Група взаємопов'язаних проектів, узгоджене управління якими дає переваги та синергію, недосяжні при роздільному управлінні (*наприклад, розробка автономного автомобіля: проекти радара, камери, автопілота, шасі*).
* **Портфоліо (Portfolio):** Сукупність проектів, програм та операційної діяльності, об'єднаних для досягнення стратегічних бізнес-цілей організації (*наприклад, все портфоліо цифрових сервісів банку*).

### 2.3. Золотий трикутник проектного менеджменту (Project Triangle)

Фундаментальна концепція балансу обмежень:

```text
                               Обсяг (Scope)
                                    ▲
                                   / \
                                  /   \
                                 /     \
                                /       \
                               /  ЯКІСТЬ \
                              /  (Quality)\
                             /             \
                            /               \
         Час (Time/Schedule) ◄───────────────► Бюджет (Cost/Budget)
```

> 💡 **Правило балансу обмежень:**
> Зміна будь-якої однієї вершини неминуче впливає на інші:
> * Якщо клієнт розширює **Обсяг (Scope)** $\implies$ потрібно збільшити **Час (Time)** або залучити більше **Бюджету (Cost)**, інакше постраждає **Якість (Quality)**.
> * Якщо вимагається скоротити **Час (Fast-tracking)** $\implies$ зростає **Бюджет** (овертайми, додаткові люди) або урізається **Обсяг**.
> * **Якість (Quality)** знаходиться в центрі трикутника як інтегральний критерій виконання вимог.

### 2.4. Проектний Менеджер (Project Manager, PM)

#### Визначення за міжнародними стандартами:
* **PMI PMBOK 7th ed.:** Особа, призначена організацією-виконавцем для керівництва проектною командою, яка відповідає за досягнення цілей проекту.
* **IPMA ICB 4.0:** Особа, відповідальна за ведення та керування проектом з метою досягнення визначених цілей, балансування обмежень (scope, time, cost, quality, risk), залучення стейкхолдерів та керівництво командою.
* **DIN 69901:** Особа, відповідальна за загальний результат проекту та досягнення його цілей у межах узгоджених обмежень.

#### Що повинен робити PM (Ділянки відповідальності):
PM не зобов'язаний писати весь код чи власноруч розробляти схеми (це неможливо у великих системах). Його завдання — **організація, координація та контроль**:

```text
               ┌────────────────────────────────────────────────────────┐
               │         Ділянки відповідальності PM                    │
               └──────────────────────────┬─────────────────────────────┘
          ┌───────────────────────┬───────┴───────┬───────────────────────┐
          ▼                       ▼               ▼                       ▼
┌───────────────────┐   ┌───────────────────┐   ┌───────────────────┐   ┌───────────────────┐
│ Створити          │   │ Організувати      │   │ Координувати      │   │ Звітувати та      │
│ середовище        │   │ роботу            │   │ і контролювати    │   │ надати результат  │
├───────────────────┤   ├───────────────────┤   ├───────────────────┤   ├───────────────────┤
│ • Набрати команду │   │ • Розподілити     │   │ • Відстежувати    │   │ • Встановити      │
│ • Зарезервувати   │   │   відповідальність│   │   прогрес задач   │   │   канали зв'язку  │
│   ресурси         │   │ • Декомпозувати   │   │ • Керувати        │   │ • Звітувати       │
│ • Обрати процеси  │   │   завдання        │   │   ризиками        │   │   стейкхолдерам   │
│ • Налагодити      │   │ • Встановити      │   │ • Контролювати    │   │ • Передати        │
│   інструментарій  │   │   пріоритети      │   │   якість і бюджет │   │   результат       │
└───────────────────┘   └───────────────────┘   └───────────────────┘   └───────────────────┘
```

### 2.5. Організація, Процеси та PMO (Project Management Office)

* **Організація (Organization):** Компанія, фірма або структурний підрозділ, що реалізує проект. Організація надає проекту ресурси, культуру, інструменти, а проект повертає результат і звітність.
* **Процеси (Processes):** Внутрішні стандарти компанії (хто приймає рішення, шаблони документів, процедури ескалації, життєві цикли).
* **PMO (Project Management Office):** Спеціалізований структурний підрозділ компанії, що виконує функції:
  1. Розвиток та уніфікація методології проектного управління;
  2. Формулювання та аудит процесів;
  3. Навчання та коучинг керівників проектів;
  4. Моніторинг здоров'я проектів портфоліо (*Project Health Check*).

### 2.6. Філософія та Цінності в проектному менеджменті
* **Особистісні цінності:** Повага, чесність, відповідальність, толерантність, самовдосконалення.
* **Організаційні цінності:** Професійність, прозорість, якість, інноваційність, клієнтоорієнтованість (*Customer Focus*), принцип постійного вдосконалення (*Kaizen*).
* У критичні моменти та за умов кризи рішення приймаються на основі цінностей!

## 3. Життєвий цикл проекту (Project Lifecycle)

**Життєвий цикл проекту (Project Lifecycle)** — це визначена послідовність фаз, через які проходить проект від моменту його ініціації до завершення.

```text
Узагальнений життєвий цикл:
┌──────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│  Ініціація   ├───►│ Планування   ├───►│  Виконання   ├───►│  Контроль    ├───►│ Завершення   │
│ (Initiation) │    │  (Planning)  │    │ (Execution)  │    │(Monitoring)  │    │  (Closing)   │
└──────────────┘    └──────────────┘    └──────────────┘    └──────────────┘    └──────────────┘
```

---

### 3.1. Моделі життєвого циклу

#### 1. Послідовна модель (Sequential / Waterfall / «Водоспад»)
* Проект розділений на суворі послідовні фази: *Запит клієнта $\to$ Вимоги $\to$ Архітектура $\to$ Дизайн $\to$ Реалізація $\to$ Тести $\to$ Впровадження*.
* Перехід на наступну фазу можливий лише після повного завершення і затвердження попередньої («Requirements Freeze», «Design Freeze»).
* **Переваги:** Чіткість плану, передбачуваність бюджету та термінів.
* **Недоліки:** Величезні ризики при зміні вимог; запізніле тестування (дефекти виявляються наприкінці).

```text
Waterfall Flow:
[Вимоги] ──► [Архітектура] ──► [Дизайн] ──► [Кодування] ──► [Тестування] ──► [Реліз]
```

#### 2. V-Модель (V-Model)
* Розвиток послідовного підходу, що ставить у відповідність кожному рівню декомпозиції вимог дзеркальний рівень інтеграції та тестування.
* Забезпечує **наскрізну простежуваність (Traceability)**:
  * **Горизонтальна простежуваність:** *Вимоги $\leftrightarrow$ Кваліфікаційні тести*; *Архітектура $\leftrightarrow$ Інтеграційні тести*; *Дизайн модулів $\leftrightarrow$ Модульні тести (Unit Tests)*.
  * **Вертикальна простежуваність:** зв'язок між вимогами різного рівня (Customer $\to$ System $\to$ Component).
* Стандарт в автомобільній (ASPICE, ISO 26262), медичній та аерокосмічній галузях.

```text
                           V-MODEL DIAGRAM
Рівень Системи:
Вимоги (Requirements) ─────────────────────────► Кваліфікаційні тести (System Acceptance)
       \                                               ▲
        ▼                                             /
  Архітектура (Architecture) ───────────► Інтеграційні тести (Integration Tests)
         \                                     ▲
          ▼                                   /
Рівень Деталей:
    Дизайн (Design) ─────────────► Модульні тести (Unit Tests)
           \                             ▲
            ▼                           /
             Реалізація / Код (Implementation)
```

#### 3. Гнучкі моделі (Agile: Scrum, Kanban, SAFe)
* Орієнтовані на змінне середовище та часті зміни вимог.
* Робота ведеться короткими ітераціями (спринтами 1–4 тижні) з отриманням працюючого інкременту продукту наприкінці кожної ітерації.
* **Scrum:** самоорганізовані невеликі команди (5–9 людей), події (Sprint Planning, Daily Standup, Review, Retrospective).
* **SAFe (Scaled Agile Framework):** масштабування Agile для великих програм зі 100+ учасниками (Agile Release Trains, каскадування цілей).

---

### 3.2. Критерії вибору моделі та Гібридні підходи

Жодна модель не є універсальною. Вибір залежить від:
1. **Визначеності вимог:** чіткі й стабільні $\implies$ Waterfall / V-Model; мінливі $\implies$ Agile.
2. **Галузевих вимог:** автопром, медицина вимагають суворої сертифікації (V-Model, ASPICE).
3. **Розміру організації та контрактної моделі:** фіксована ціна (*Fixed Price*) частіше вимагає Waterfall, погодинна оплата (*Time & Material*) підходить для Agile.

> 💡 **Реальний інженерний приклад: Гібридна модель в Automotive / IoT:**
> * **Рівень Організації / Автомобіля (Vehicle Level):** Послідовний підхід (Waterfall / QMS);
> * **Рівень Продукту / Системи (System/ECU Level):** V-модель (ASPICE V-Cycle);
> * **Рівень розробки ПЗ (SW Development Level):** Гнучкий підхід (Agile, Scrum, Kanban).

---

### 3.3. Майлстоуни (Milestones)

**Майлстоун (Milestone / Віха)** — це ключова контрольна точка у графіку проекту, що фіксує досягнення суттєвого проміжного результату або завершення важливого етапу.

```text
Типова шкала майлстоунів проекту:
───[ M1 ]───────────────[ M2 ]───────────────[ M3 ]───────────────[ M4 ]───────────────[ M5 ]──► Час
   RFQ / Kickoff      Reqs Freeze      Arch Approval      Design Freeze     Start of Production
                                                                                   (SOP)
```

#### Результати проходження Майлстоуну керівництвом (Gate Review):
1. **Затверджено (Pass):** Проміжні цілі виконано повністю, дозвіл переходити до наступної фази.
2. **Умовно затверджено (Conditional Pass):** Дозвіл рухатися далі надано з обов'язковим закриттям виявлених дефектів/боргів до визначеної дати.
3. **Відхилено (Fail):** Цілі не досягнуто, проект зупиняється на поточному етапі до усунення прогалин.

## ❓ Питання для самоперевірки
1. Чим відрізняється проектна діяльність від регулярної операційної діяльності (Operations)?
2. Які вершини утворюють «Золотий трикутник» проектного менеджменту, і що знаходиться в його центрі?
3. У чому полягає фундаментальна різниця між Програмою (Program) та Портфоліо (Portfolio)?
4. Чому V-модель є обов'язковою для критичних систем (автомобільна галузь, авіація), і що означає поняття горизонтальної та вертикальної простежуваності (Traceability)?

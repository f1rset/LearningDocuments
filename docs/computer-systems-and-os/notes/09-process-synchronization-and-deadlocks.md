# 09. Синхронізація процесів та взаємні блокування (Process Synchronization & Deadlocks)

## 🎯 Ключові концепції (Core Concepts)
1. **Проблема критичної секції (Critical Section Problem):** Взаємне виключення (Mutual Exclusion), Прогрес (Progress), Обмежене очікування (Bounded Waiting).
2. **Стан гонитви (Race Condition) та апаратна атомарність:** Інструкції Test-and-Set та Compare-and-Swap (CAS).
3. **Примітиви синхронізації:** Спінлоки (Spinlocks), М'ютекси (Mutexes), Семафори Дейкстри (Semaphores), Умовні змінні (Condition Variables) та блокування читання-запису (RW-Locks).
4. **Класичні задачі синхронізації:** Виробник-Споживач (Producer-Consumer), Читачі-Письменники (Readers-Writers), Обідаючі філософи (Dining Philosophers).
5. **Взаємне блокування (Deadlock):** Чотири умови Кофмана (Coffman Conditions) та граф виділення ресурсів (RAG).
6. **Стратегії боротьби з дедлоками:** Запобігання (Prevention), Уникнення (Avoidance - Алгоритм банкіра), Виявлення (Detection) та алгоритм страуса.

## 1. Проблема критичної секції та стан гонитви (Race Condition)

**Стан гонитви (Race Condition)** — ситуація, коли результат виконання програми залежить від непередбачуваного порядку перемикання потоків планувальником при доступі до спільного ресурсу.

* **Критична секція (Critical Section):** Ділянка коду, в якій здійснюється читання або модифікація спільних змінних чи ресурсів.

```text
  Потік 1:                     Потік 2:
  load counter (%eax = 5)
                               load counter (%ebx = 5)
  add $1, %eax (%eax = 6)
                               sub $1, %ebx (%ebx = 4)
  store %eax into counter
                               store %ebx into counter (ЗАПИСАВ 4 ЗАМІСТЬ 5!)
```

### 1.1. Три обов'язкові вимоги коректного розв'язку:
1. **Взаємне виключення (Mutual Exclusion):** Якщо потік $T_i$ виконує свою критичну секцію, жоден інший потік не може перебувати у своїй критичній секції.
2. **Прогрес (Progress):** Якщо жоден потік не перебуває в критичній секції, вибір наступного потоку для входу не може відкладатися нескінченно.
3. **Обмежене очікування (Bounded Waiting):** Існує фіксована межа на кількість разів, яку інші потоки можуть зайти в критичну секцію після того, як потік подав запит на вхід (захист від голодування).

## 2. Апаратні примітиви атомарності (Hardware Atomicity)

Сучасні процесори надають неподільні (Atomic RMW - Read-Modify-Write) інструкції з блокуванням шини кешу (`LOCK` префікс у x86):

### 2.1. Compare-and-Swap (CAS / `cmpxchg`)
Атомарно порівнює значення в пам'яті з очікуваним $V_{\text{expected}}$, і якщо вони рівні — записує нове значення $V_{\text{new}}$:

```c
bool compare_and_swap(int* ptr, int expected, int new_value) {
    // Виконується атомарно апаратурою за 1 інструкцію:
    if (*ptr == expected) {
        *ptr = new_value;
        return true;  // Успіх
    }
    return false;     // Невдача (значення було змінено іншим потоком)
}
```
*(CAS є основою всіх неблокуючих Lock-Free структур даних та атоміків `std::atomic`)*.

## 3. Програмні примітиви синхронізації (Synchronization Primitives)

```text
  Спінлок (Spinlock)          М'ютекс (Mutex)              Семафор (Semaphore)
  [ Активне очікування ]      [ Спить у черзі ОС ]         [ Лічильник ресурсів N ]
  while (!try_lock());        lock() -> Blocked/Sleep      P() / sem_wait() -> N--
  - Немає context switch      - Віддає CPU іншим           V() / sem_post() -> N++
  - Спалює 100% CPU           - Витрати на пробудження     - Сигналізування між потоками
```

### 3.1. Спінлоки (Spinlocks)
Потік крутиться у нескінченному циклі (Busy Waiting), постійно перевіряючи блокування.
* *Застосування:* Виключно для короткочасних блокувань (кілька тактів) у коді ядра ОС (в обробниках переривань, де не можна засинати).

### 3.2. М'ютекси (Mutexes / `pthread_mutex_t`)
Двійкове блокування зі сном. Якщо м'ютекс зайнятий, потік переходить у стан `Waiting` (засинає), а ядро віддає CPU іншим задачам.

### 3.3. Семафори Дейкстри (Semaphores)
Захищений цілочисельний лічильник $S \ge 0$ з двома атомарними операціями:
* **`wait(S)` (або $P$ / `sem_wait`):** Якщо $S > 0$, зменшує $S$ на 1. Якщо $S = 0$, потік блокується.
* **`signal(S)` (або $V$ / `sem_post`):** Збільшує $S$ на 1 і будить один із заблокованих потоків.
* **Двійковий семафор ($S=1$):** Працює як м'ютекс.
* **Лічильний семафор ($S=N$):** Керує пулом із $N$ однакових ресурсів.

### 3.4. Умовні змінні (Condition Variables / `pthread_cond_t`)
Дозволяють потоку заснути всередині м'ютекса до настання певної умови:
```c
pthread_mutex_lock(&mutex);
while (!data_ready) {                  // ⚠️ ЗАВЖДИ у циклі while (захист від Spurious Wakeups)
    pthread_cond_wait(&cond, &mutex);  // Атомарно відпускає м'ютекс і засинає
}
// Обробка даних...
pthread_mutex_unlock(&mutex);
```

## 4. Класичні задачі синхронізації

### 4.1. Задача "Виробник-Споживач" (Producer-Consumer / Bounded Buffer)
Буфер фіксованого розміру $N$. Виробник не повинен писати у повний буфер, споживач не повинен читати з порожнього.

```c
sem_t empty_slots; // Початково = N
sem_t full_slots;  // Початково = 0
pthread_mutex_t mutex;

void producer() {
    sem_wait(&empty_slots);
    pthread_mutex_lock(&mutex);
    // Додати елемент у буфер
    pthread_mutex_unlock(&mutex);
    sem_post(&full_slots);
}

void consumer() {
    sem_wait(&full_slots);
    pthread_mutex_lock(&mutex);
    // Забрати елемент з буфера
    pthread_mutex_unlock(&mutex);
    sem_post(&empty_slots);
}
```

## 5. Взаємні блокування (Deadlocks)

**Дедлок (Deadlock)** — стан системи, за якого кілька процесів заблоковані в очікуванні ресурсів, які утримуються один одним, і жоден не може продовжити виконання.

```text
           [Процес P1] -------- Утримує --------> [Ресурс R1]
                ^                                      |
                |                                      |
             Чекає                                   Чекає
                |                                      |
                |                                      v
           [Ресурс R2] <------- Утримує -------- [Процес P2]
```

### 5.1. Чотири необхідні умови Кофмана (Coffman Conditions)
Дедлок виникає **тоді й лише тоді**, коли одночасно виконуються всі 4 умови:
1. **Взаємне виключення (Mutual Exclusion):** Ресурси неподільні (тільки один процес у момент часу).
2. **Утримання та очікування (Hold and Wait):** Процес утримує хоча б один ресурс і водночас чекає виділення інших.
3. **Відсутність витискання (No Preemption):** Ресурс не можна примусово відібрати у процесу.
4. **Кругове очікування (Circular Wait):** Існує ланцюг процесів $\{P_0, P_1, \dots, P_n\}$, де $P_0$ чекає ресурс від $P_1$, $P_1$ від $P_2$, ..., а $P_n$ чекає від $P_0$.

### 5.2. Методи боротьби з дедлоками

1. **Запобігання (Prevention):** Анулювання хоча б однієї з 4 умов Кофмана.
   * *Руйнування кругового очікування (Lock Ordering):* Введення глобального порядку на ресурси ($R_1 < R_2 < R_3$) та вимога захоплювати м'ютекси **суворо за зростанням їхніх номерів**.
2. **Уникнення (Avoidance - Алгоритм банкіра Дейкстри):**
   Ядро аналізує кожен запит на ресурс і задовольняє його лише тоді, коли система залишається в **безпечному стані (Safe State)** (існує хоча б одна послідовність завершення всіх процесів).
3. **Виявлення та відновлення (Detection & Recovery):** Періодичний пошук циклів у графі очікування (Wait-For Graph) та примусове вбивство (`SIGKILL`) одного з процесів для розриву дедлоку.
4. **Алгоритм страуса (Ostrich Algorithm):** Ігнорування проблеми через рідкісність події (підхід за замовчуванням у Linux/Windows).

---

## ⚠️ Підводні камені та типові помилки (Pitfalls)

1. **Deadlock при перехресному захопленні м'ютексів:**
   Потік 1 бере `Lock(A)` потім `Lock(B)`, а Потік 2 бере `Lock(B)` потім `Lock(A)`. У $100\%$ випадків рано чи пізно виникне дедлок (завжди використовуйте `std::lock(a, b)` у C++).
2. **Використання `if` замість `while` з умовними змінними:**
   Через **хибні пробудження (Spurious Wakeups)** операційної системи потік може прокинутися від `pthread_cond_wait`, коли умова ще не виконана. Очікування обов'язково має бути обгорнуте в цикл `while (!ready)`.
3. **Забутий unlock при виході з функції (Exception Safety):**
   Викидання винятку або передчасний `return` до виклику `unlock()` назавжди блокує м'ютекс. Використовуйте ідіому RAII (`std::lock_guard` / `std::unique_lock`).

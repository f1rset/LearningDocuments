# 12. Віртуалізація, контейнеризація та безпека ОС (Virtualization, Containers & OS Security)

## 🎯 Ключові концепції (Core Concepts)
1. **Апаратна віртуалізація (Hypervisors):** Гіпервізори 1-го типу (Bare-Metal / KVM, ESXi) проти 2-го типу (Hosted / VirtualBox).
2. **Апаратні розширення віртуалізації (Intel VT-x / AMD-V):** Режими VMX Root / Non-Root, `VMENTRY`/`VMEXIT` та вкладені таблиці сторінок (EPT / SLAT).
3. **Контейнеризація vs Віртуальні машини:** Спільне ядро проти ізольованої гостьової ОС.
4. **Ядерні механізми Linux для контейнерів:**
   * **Namespaces (Простори імен):** Ізоляція видимості системних ресурсів (`pid`, `net`, `mnt`, `ipc`, `uts`, `user`).
   * **Cgroups (Control Groups v2):** Обмеження та тарифікація ресурсів CPU, пам'яті та I/O.
   * **OverlayFS / UnionFS:** Шарувата файлова система образів контейнерів.
5. **Моделі контролю доступу:** Дискреційний (DAC - POSIX `rwx`) проти Мандатного (MAC - SELinux, AppArmor).
6. **Сучасні механізми апаратного захисту пам'яті:** ASLR, Stack Canaries, біт заборони виконання DEP / NX ($W \oplus X$).

## 1. Апаратна віртуалізація (Hypervisors & Hardware-Assisted Virtualization)

Віртуалізація створює ілюзію повної незалежної апаратної машини (Virtual Machine - VM) для гостьової операційної системи.

```text
      ГІПЕРВІЗОР 1-ГО ТИПУ (Bare-Metal)           ГІПЕРВІЗОР 2-ГО ТИПУ (Hosted)
  +---------------------------------------+   +---------------------------------------+
  | [Гостьова ОС 1]   | [Гостьова ОС 2]   |   | [Гостьова ОС 1]   | [Гостьова ОС 2]   |
  +-------------------+-------------------+   +-------------------+-------------------+
  |  Гіпервізор Type-1 (KVM, ESXi, Xen)   |   |  Гіпервізор Type-2 (VirtualBox, VMWare)|
  +---------------------------------------+   +---------------------------------------+
  |       Фізичне залізо (Bare-Metal)     |   |  Хостова ОС (Host OS: Linux, Windows) |
  +---------------------------------------+   +---------------------------------------+
                                              |       Фізичне залізо (Bare-Metal)     |
                                              +---------------------------------------+
```

### 1.1. Апаратна підтримка віртуалізації (Intel VT-x / AMD-V)
Раніше інструкції Ring 0 гостьової ОС не могли виконуватися на реальному CPU без важкої бінарної трансляції. Сучасні процесори додали спеціальні апаратні режими:
* **VMX Root Operation:** Режим роботи гіпервізора (повний контроль над апаратурою).
* **VMX Non-Root Operation:** Режим роботи гостьової ОС. Коли гостьова ОС намагається виконати критичну системну інструкцію, процесор апаратно генерує подію **`VMEXIT`** і передає керування гіпервізору.
* **Вкладені таблиці сторінок (EPT - Extended Page Tables / SLAT):**
  Дворівнева трансляція адрес:
  $$\text{Guest Virtual Address} \xrightarrow{\text{Guest Page Table}} \text{Guest Physical Address} \xrightarrow{\text{EPT (Апаратний MMU)}} \text{Host Physical Address}$$

## 2. Контейнеризація (Containerization / OS-Level Virtualization)

Контейнери — це не віртуалізація заліза, а **ізольовані групи процесів, що виконуються безпосередньо на спільному хостовому ядрі Linux**.

```text
         ВІРТУАЛЬНІ МАШИНИ (VM)                       КОНТЕЙНЕРИ (Docker)
  +-----------------------------------+   +-----------------------------------+
  | Додаток A     | Додаток B         |   | Додаток A     | Додаток B         |
  +---------------+-------------------+   +---------------+-------------------+
  | Бібліотеки    | Бібліотеки        |   | Бібліотеки    | Бібліотеки        |
  +---------------+-------------------+   +---------------+-------------------+
  | Гостьова ОС 1 | Гостьова ОС 2     |   | Ізоляція: Namespaces + Cgroups    |
  +---------------+-------------------+   +-----------------------------------+
  | Гіпервізор (KVM / Hyper-V)        |   | Спільне єдине ядро Linux (Host)   |
  +-----------------------------------+   +-----------------------------------+
  | Фізичне залізо                    |   | Фізичне залізо                    |
  +-----------------------------------+   +-----------------------------------+
```

| Критерій | Віртуальна машина (VM) | Контейнер (Container) |
| :--- | :--- | :--- |
| **Архітектура** | Повна емуляція заліза + окреме ядро | Спільне ядро хостової ОС |
| **Час старту** | Десятки секунд / хвилини | Мілісекунди |
| **Використання пам'яті**| Гігабайти (дублювання ядер ОС) | Мегабайти (лише пам'ять процесу) |
| **Продуктивність I/O / CPU**| Накладні витрати на EPT/емуляцію ($5\text{--}15\%$) | Майже $100\%$ швидкість нативного заліза (Near-native) |
| **Рівень ізоляції** | Максимальний (апаратні межі VT-x) | Програмний (спільне ядро ОС) |

## 3. Ядерні механізми Linux для реалізації контейнерів

Контейнер (Docker, containerd, LXC) створюється комбінацією 3 ядерних компонентів:

### 3.1. Простори імен Linux (Namespaces) — "Що процес може бачити"
1. **`pid`:** Ізольоване дерево процесів. Всередині контейнера головний процес має `PID 1`, хоча на хості він має реальний `PID 24580`.
2. **`net`:** Власний мережевий стек: віртуальні інтерфейси (`eth0`), власна таблиця маршрутизації, IP-адреси та правила iptables/nftables.
3. **`mnt`:** Власні точки монтування файлових систем.
4. **`ipc`:** Ізоляція черг повідомлень POSIX, семафорів та спільної пам'яті.
5. **`uts`:** Власне мережеве ім'я хоста (Hostname).
6. **`user`:** Відображення `UID 0` (root) всередині контейнера на безпечного непривілейованого користувача `UID 10001` на хостовій машині.

### 3.2. Контрольні групи (Control Groups - Cgroups v2) — "Скільки ресурсів процес може спожити"
* **`cpu.max`:** Обмеження квантів процесорного часу через механізм CFS Quota (наприклад, виділення рівно 2.5 ядер CPU).
* **`memory.max`:** Жорсткий ліміт оперативної пам'яті. При перевищенні ліміту ядро викликає OOM Killer лише всередині цієї групи (`cgroup OOM`).
* **`io.max`:** Обмеження швидкості читання/запису на диск (IOPS та байт/с).

### 3.3. Шарувата файлова система (OverlayFS)
Образ Docker складається з масиву шарів, доступних лише для читання (**LowerDir / Read-Only Layers**).
При запуску контейнера поверх них монтується тонкий шар запису (**UpperDir / Read-Write Layer**). Якщо контейнер змінює файл з базового образу, OverlayFS виконує копіювання файлу наверх (**Copy-up**) і модифікує лише локальну копію.

```text
  [ UpperDir: Read-Write Шар контейнера ] -> Нові або змінені файли
  =================================================================
  [ LowerDir: Read-Only Шар 2 (Python)  ]
  [ LowerDir: Read-Only Шар 1 (Ubuntu)  ] -> Спільні незмінні шари
```

## 4. Безпека операційних систем та захист пам'яті

### 4.1. Моделі контролю доступу (Access Control)
* **DAC (Discretionary Access Control - Дискреційний):** Традиційна модель UNIX. Власник файлу сам визначає права читання/запису/виконання (`rwxrwxrwx`) для користувача, групи та інших.
* **MAC (Mandatory Access Control - Мандатний / SELinux, AppArmor):** Система безпеки базується на строгих політиках та мітках (Labels), які призначаються адміністратором. Навіть суперкористувач `root` не може отримати доступ до ресурсу, якщо це заборонено політикою безпеки SELinux.
* **Linux Capabilities:** Розбиття всемогутності суперкористувача `root` на окремі дрібні привілеї (`CAP_NET_BIND_SERVICE` для порту 80, `CAP_SYS_ADMIN`, `CAP_KILL`).

### 4.2. Сучасні апаратні та програмні механізми захисту бінарного коду

```text
               МЕХАНІЗМИ ЗАХИСТУ БІНАРНОГО КОДУ
                               |
       +-----------------------+-----------------------+
       |                       |                       |
  [ ASLR / PIE ]        [ Stack Canaries ]        [ DEP / NX ($W \oplus X$) ]
  Рандомізація адрес    Секретний маркер перед    Сторінка або записувана,
  пам'яті при старті    адресою повернення на     або виконувана, але
  (Стек, Купа, Бібл.)   стеку (перевірка overflow)НЕ ОБИДВА ОДНОЧАСНО!
```

1. **DEP / NX Bit (Data Execution Prevention / $W \oplus X$ — Write XOR Execute):**
   Апаратний захист на рівні таблиць сторінок (PTE). Сторінки стека та купи позначаються бітом `NX = 1` (Non-Executable). Будь-яка спроба виконати зловмисний шеллкод, завантажений на стек, негайно викличе аварійне завершення процесу.
2. **ASLR (Address Space Layout Randomization):**
   При кожному новому запуску програми ядро рандомізує базові адреси стека, купи та бібліотек (`libc.so`). Атакувальник не може заздалегідь знати адресу цільової функції (захист від Return-to-libc та ROP-атак).
3. **Канарки на стеку (Stack Canaries / Stack Cookies):**
   Компілятор `gcc` розміщує випадкове 8-байтне число між локальними змінними та адресою повернення функції. Перед поверненням з функції (`ret`) значення канарки перевіряється. Якщо відбулося переповнення буфера і канарка пошкоджена — програма негайно зупиняється (`*** stack smashing detected ***`).

## ⚠️ Підводні камені та типові помилки (Pitfalls)

1. **Запуск процесів всередині контейнера під `root`:**
   За замовчуванням `root` всередині контейнера має той самий `UID 0`, що й root хостової системи. У разі вразливості типу Container Escape атакувальник отримує повний контроль над усім фізичним сервером. (Використовуйте `USER nonroot` або User Namespaces).
2. **Сліпа довіра до прапорців контейнеризатора (`--privileged` у Docker):**
   Прапорець `--privileged` відключає всі механізми ізоляції (дозволяє прямий доступ до всіх пристроїв `/dev`, вимикає AppArmor/SELinux та повертає всі Capabilities), перетворюючи контейнер на звичайний неізольований процес.

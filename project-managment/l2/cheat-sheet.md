## 📌 TL;DR — Найголовніше за 60 секунд
* **Продукт vs Проект:** Проект — тимчасова діяльність. Продукт — результат проекту, який живе через стадії розробки, продажу, підтримки та виведення з ринку.
* **BOM (Bill of Materials):** Інженерний перелік деталей для створення виробу. Включає: *Assembly* (складальні одиниці), *Parts* (одиничні деталі), *Materials* (незлічувані матеріали).
* **Стратегія Make or Buy:** Виготовляти самостійно (унікальне ноу-хау) чи купувати готове (стандартизовані компоненти).
* **Ієрархія вимог:** Customer Reqs (Чого хоче користувач) $\to$ System Reqs (Що робить система / Black Box) $\to$ Design Reqs (Архітектура та код / White Box).
* **Типи вимог:** 
  * *Функціональні:* Що система робить (поведінка, дії).
  * *Нефункціональні:* Як добре працює (швидкодія, пам'ять, безпека, надійність).
* **Вимоги за SMART:** Specific (конкретні), Measurable (вимірювані), Attainable (досяжні), Relevant (доречні), Time-bound (обмежені в часі).
* **Нотація INCOSE:** `When <Condition>, the <System> shall <Action> within <Constraints>`.
* **User Story:** `As a <User>, I want <Feature>, so that <Value>`.

## 📊 Матриця підходів до розробки продукту

| Підхід | Характеристика релізів | Коли обирати |
| :--- | :--- | :--- |
| **Waterfall** | 1 фінальний реліз наприкінці | Жорстко зафіксовані контракти, стабільні вимоги |
| **V-Model** | Поетапне багаторівневе тестування | Вимоги безпеки, критичні системи (Auto, Med, Aero) |
| **Incremental** | Релізи частинами: Модуль 1 $\to$ Модуль 2 $\to$ Модуль 3 | Модульні системи, коли потрібна рання функціональність |
| **Iterative** | Регулярне поліпшення та рефакторинг всієї системи | Стартапи, нечіткі вимоги, дослідження ринку (R&D) |

## 📐 Шаблони формулювання вимог

### 1. Формалізований шаблон INCOSE:
```text
[Умова] + [Суб'єкт] + [Модальність] + [Дія] + [Об'єкт] + [Обмеження]
Приклад:
"When battery level drops below 15%, the system shall display a low-power warning within 1 second."
```

### 2. Шаблон User Story:
```text
"As a [користувач], I need [можливість], so that [бізнес-вигода]"
Приклад:
"As a driver, I need blind-spot warning on the side mirror, so that I can change lanes safely."
```

## 🛠️ Інженерні евристики роботи з вимогами
1. **Золоте правило тестування:** Якщо вимогу не можна протестувати за чітким критерієм Pass/Fail — перепишіть вимогу.
2. **Атомарність:** Одна вимога = одна думка. Уникайте сполучників «і», «а також» у тексті однієї вимоги.
3. **Клієнт не завжди правий:** PM та інженерна команда повинні критично аналізувати запити клієнта і вчасно аргументовано відхиляти технічно неможливі речі.
